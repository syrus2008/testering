I. Vision et périmètre
1. Mission produit
ACET est une application locale d’intelligence d’évolution logicielle spécialisée dans la comparaison longitudinale de composants binaires. Elle ingère des artefacts fournis par l’utilisateur, construit des observations et des builds, extrait des faits reproductibles, compare les fonctions entre versions, construit des lignées, détecte des changements inhabituels et produit des rapports inspectables.
ACET-PROD-001 — But
Le produit DOIT réduire l’espace d’investigation d’un analyste sans transformer une corrélation ou un score de similarité en affirmation fonctionnelle non démontrée.
ACET-PROD-002 — Frontière défensive
ACET NE DOIT PAS exécuter les artefacts importés, charger un driver analysé, injecter dans un processus, contourner un mécanisme de protection ou automatiser une interaction avec un processus protégé.
ACET-PROD-003 — Généricité
Le Core ne DOIT contenir aucune branche métier codée en dur pour EAC, BattlEye ou un autre produit. Les spécificités éventuelles sont des Product Profiles déclaratifs.
2. Principes non négociables
Principe
Règle
Fact ≠ inference
Les faits observés sont immuables ; les inférences sont recalculables et versionnées.
No magic score
Les dimensions d’anomalie restent séparées ; aucun score unique n’est présenté comme vérité.
Unmatched ≠ new
Une fonction non appariée n’est pas automatiquement classée comme nouvelle.
Build ≠ observation
Une observation date la présence d’un build/artefact ; elle n’en crée pas une nouvelle identité.
Explainability
Toute conclusion doit exposer sa provenance et ses preuves.
Reproducibility
Chaque analyse enregistre versions, paramètres, entrées et schémas.
Offline-first
Le cœur fonctionne sans réseau ; aucune donnée binaire n’est envoyée implicitement.
Graceful degradation
L’absence d’un moteur optionnel produit un résultat partiel, pas l’échec global.

ACET-ARCH-001 — Indépendance UI

ACET-DB-001 — Foreign keys
PRAGMA foreign_keys=ON est obligatoire.
ACET-DB-002 — WAL
SQLite utilise WAL sauf incompatibilité détectée ; l’application journalise tout fallback.
ACET-DB-003 — Migrations
Une migration suit backup → migration transactionnelle → integrity_check → commit. En cas d’échec, rollback et restauration de l’état précédent.
IV. Import et modèle Build
11. Pipeline d’import
DISCOVER → PREVIEW → VALIDATE → HASH → COPY → VERIFY → CLASSIFY → COMMIT → OPTIONAL ANALYZE
ACET-IMP-001 — Aucune exécution
La détection de format et métadonnées est statique. Aucun fichier importé n’est exécuté.
ACET-IMP-002 — Copie vérifiée
Après copie vers le store, ACET recalcule SHA-256 et compare au hash source avant commit DB.
ACET-IMP-003 — Doublon artefact
Si SHA-256 existe déjà, les bytes ne sont pas recopiés ; une nouvelle référence et/ou observation est créée.
ACET-IMP-004 — Doublon build
Si build_fingerprint existe, ACET propose Ajouter observation / Ouvrir existant / Annuler. Il ne crée pas silencieusement un doublon.
ACET-IMP-005 — Near duplicate
Une forte similarité de composants peut déclencher un avertissement mais ne fusionne jamais automatiquement deux builds.
ACET-IMP-006 — Import incomplet
Un build peut être PARTIAL. Les composants manquants sont UNKNOWN, jamais implicitement absents.
12. Fingerprint du build
build_fingerprint = SHA256(  canonical_json(    sorted([      { role, artifact_sha256, purpose, ordinal }      for every component artifact    ])  ))
Les labels de version, dates, chemins locaux et noms de fichiers ne participent pas au fingerprint technique.

24. Baseline historique
Pour chaque produit/composant, ACET maintient des distributions robustes : médiane, MAD, percentiles et historique. Les classes NORMAL / UNUSUAL / EXTREME sont déterminées par un profil statistique versionné. Aucune distribution n’est partagée implicitement entre produits différents.
VII. Jobs, reprise et performance
25. Machine d’état Job
QUEUED  ↓PREPARING  ↓RUNNING ↔ PAUSING → PAUSED → RESUMING  ↓POST_PROCESSING  ↓COMPLETEDSide states:CANCELLING → CANCELLEDFAILED_RETRYABLEFAILED_PERMANENTINTERRUPTED → RECOVERINGBLOCKED_DEPENDENCY
ACET-JOB-001 — Checkpoint
Chaque étape durable écrit un checkpoint transactionnel.
ACET-JOB-002 — Annulation
Annuler un Analysis Run ne supprime pas les résultats déjà terminés et compatibles avec le cache.
ACET-JOB-003 — Heartbeat
Les workers lourds émettent un heartbeat ; absence prolongée mène à HUNG puis arrêt contrôlé.
ACET-JOB-004 — Priorité
Priorités LOW/NORMAL/HIGH/INTERACTIVE avec aging pour éviter la famine.

40. Datasets initiaux
Le benchmark initial utilise : (1) un petit dataset de démonstration open source distribué avec ACET ; (2) BinKit 2.0 comme corpus externe pour robustesse compilateur/optimisation ; (3) projets open source compilés par ACET CI pour patches connus ; (4) corpus anti-cheat apporté légalement par l’utilisateur, jamais redistribué par défaut.
ACET-BEN-001 — Blind evaluation
Pour les cas ground truth, le détecteur ne reçoit pas le label attendu pendant l’analyse.
ACET-BEN-002 — Lineage metrics
Mesurer purity, fragmentation, wrong merge, wrong split et recovery multi-version.
ACET-BEN-003 — Calibration
Un nombre affiché comme probabilité n’est autorisé qu’après calibration empirique documentée ; sinon afficher classes de force.
41. Regression gates
Required release gates (initial policy):- no schema migration failure on supported fixtures- no deterministic golden-test mismatch- no critical false-new regression above configured tolerance- no lineage recall regression above configured tolerance- no UI-blocking operation &gt; configured threshold- all mandatory acceptance tests green

59. Validation de complétion des moteurs
Un code de retour 0 ne constitue jamais à lui seul la preuve qu’une analyse est complète. Chaque provider doit produire un Completion Manifest ACET et ACET doit valider les invariants de sortie.
completion-manifest.json{  "protocol_version": 1,  "provider_id": "...",  "provider_version": "...",  "run_id": "...",  "started_at": "...",  "finished_at": "...",  "termination": "normal|timeout|killed|crash|unknown",  "engine_exit_code": 0,  "engine_reported_errors": 0,  "engine_reported_warnings": 0,  "expected_outputs": [...],  "present_outputs": [...],  "output_checksums": {...},  "analysis_counts": {...},  "completion_state": "complete|partial|invalid"}
ACET-ENG-001 — Exit code insuffisant
Le Supervisor DOIT combiner exit code, completion manifest, présence/checksum des sorties, compteurs et analyse des erreurs structurées avant de déclarer un processor COMPLETED.
ACET-ENG-002 — Résultat partiel Ghidra
Un timeout ou une exception interne détectée produit PARTIAL/INVALID selon les sorties réellement validées ; jamais COMPLETED par défaut.
ACET-ENG-003 — Log parser versionné
Chaque provider peut posséder un parser de diagnostics versionné. Une règle de log n’est pas un fait scientifique : elle est stockée comme mécanisme de validation du provider.
60. Supervision Windows des processus
Chaque arbre de processus externe doit être placé dans un Windows Job Object dédié. Les enfants héritent du Job Object ; la fermeture/annulation dure utilise la terminaison du Job Object afin d’éviter les descendants orphelins.
ACET-WIN-001 — Job Object
Tout provider externe lancé sous Windows DOIT être associé à un Job Object ACET avec politique kill-on-close lorsque compatible.
ACET-WIN-002 — Two-stage termination
Annulation : demande gracieuse → délai configurable → TerminateJobObject. ACET journalise la méthode de terminaison.
ACET-WIN-003 — Pipe safety
Les stdout/stderr lourds sont drainés vers fichiers bornés/rotation ou lecteurs asynchrones ; le Supervisor ne dépend pas d’un EOF de pipe pour conclure qu’un Job Object est terminé.

ACET-SCI-003 — Extraction quality
La qualité de désassemblage/extraction est une dimension explicite de reliability ; un mauvais function boundary recovery ne doit pas être interprété comme changement logiciel.

QBinDiff n’est pas lancé automatiquement au-delà du seuil validé de fonctions/budget mémoire du profil. Le seuil initial doit rester conservateur et être calibré.
ACET-QBD-002 — Experimental label
Les résultats QBinDiff sont identifiés comme provider expérimental tant que les regression gates définis pour son contexte ne sont pas atteints.
70. Politique BinDiff/BinExport
ACET-BDF-001 — Official structural provider
BinDiff/BinExport devient un provider structurel officiel de DEEP@2 et un provider facultatif de STANDARD@2 si installé dans l’Engine Pack.
ACET-BDF-002 — Known incompatibility handling
Les erreurs connues de BinExport/BinDiff sur certains régimes de binaires produisent SKIPPED_KNOWN_LIMITATION ou FAILED_PROVIDER, jamais une conclusion fonctionnelle.
ACET-BDF-003 — Result size
Avant diff de très gros inputs, ACET estime tailles/limites provider et peut refuser proprement une combinaison susceptible de dépasser une limite de format ou de mémoire.
71. Politique Ghidra
ACET-GHD-004 — Analyzer profile
La liste des analyzers Ghidra activés/désactivés fait partie du Analysis Profile et de son hash.
ACET-GHD-005 — Timeout double
ACET utilise le timeout natif Ghidra lorsque pertinent ET un watchdog externe Supervisor ; aucun des deux n’est considéré suffisant seul.
ACET-GHD-006 — Project isolation
Chaque traitement utilise un projet/workdir non partagé simultanément, évitant les conflits de projet headless.

92. Definition of Done v2.0
ACET n’est « clé en main » que si la totalité du parcours utilisateur et du cycle de vie logiciel est couverte : installation signée, self-test, création/import, analyse avec supervision robuste, résultats explicables et calibrés, reprise après incident, stockage cohérent, sauvegarde/restauration, export/import versionné, mise à jour vérifiée et rollback, diagnostic/support, puis désinstallation sans perte de données. Les critères ACC-001 à ACC-100 constituent le minimum de conformité 1.0 ; aucun critère critique de sécurité, données, reproductibilité ou recovery ne peut être reporté après la release stable.

123. Definition of Done finale
ACET 1.0 est prêt à être qualifié de « clé en main » lorsque : (1) toutes les exigences MUST ont une traçabilité complète ; (2) ACC-001 à ACC-150 sont satisfaits ou, pour les critères explicitement manuels, disposent d’un protocole signé/versionné ; (3) les fault injections critiques sont vertes ; (4) les invariants globaux sont instrumentés ; (5) les benchmarks définissent le domaine de validité scientifique ; (6) les dépendances et licences sont fermées ; (7) le Release Evidence Bundle est complet ; et (8) le scénario Full Lifecycle ACC-150 réussit sur machines Windows propres. Tout problème futur non anticipé précisément doit alors être absorbé par une taxonomie, un état sûr, une stratégie de confinement/recovery et une voie de diagnostic déjà définis.
124. Ce que la spécification ne peut honnêtement garantir
Aucune spécification ne peut garantir l’absence mathématique de bug dans des systèmes tiers, l’OS, le matériel ou le code futur. La garantie recherchée ici est plus utile : absence de catégorie non traitée dans le périmètre défini, refus des états inconnus non classifiés, conservation des données et de la provenance, et comportement sûr lorsqu’une hypothèse devient invalide. Les éléments volontairement hors périmètre restent explicitement listés en §91 et ne doivent pas être réintroduits implicitement pendant le développement.
